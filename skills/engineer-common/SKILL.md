# 工程师通用规范

以下规范适用于所有工程师角色，描述完整的开发流程和质量基准。各角色在此基础上有差异化的技术栈和质量要求。

## 核心原则

1. **一次只做一个任务**: 聚焦于分配的任务，不扩大范围
2. **独立分支开发**: 每个任务从 dev 创建独立 feature 分支
3. **先拉取再合并**: 合并到 dev 前必须先拉取最新代码、解决冲突
4. **自测通过**: 合并前确保代码能正常运行
5. **最小变更**: 只修改与任务相关的代码，不做无关重构

## 开发流程

### 步骤 1: 接收任务

技术主管会传递给你：
- **任务描述**: 要实现的功能和验收标准
- **技术栈**: 对应领域的框架和工具
- **参考文档**: 需求文档、技术设计文档

### 步骤 2: 准备工作

1. 检查当前工作目录和 git 状态: `git status`
2. 确认在 dev 分支上: `git checkout dev`
3. 拉取最新 dev 代码: `git pull origin dev`
4. 阅读相关的需求文档和技术设计文档
5. 了解现有代码架构和模块
6. **制定执行计划**: 将任务拆解为 2-5 个检查点，在开始编码前告知技术主管

### 步骤 3: 创建 feature 分支

```bash
git checkout -b feature/<任务名>
```

### 步骤 4: 编码实现（按检查点执行）

#### 检查点汇报

按执行计划中的检查点逐个实现，**每个检查点完成后**向技术主管汇报：

```markdown
## 检查点报告 — <检查点名>

### 完成内容
- <完成的工作>

### 状态
- ✅ 本检查点完成

### 下一步
- 下一个检查点: <名称>

### 是否需要技术主管介入
- 是 / 否（如选择"是"，说明原因）
```

#### 卡住协议

如果在执行过程中遇到无法解决的问题，不要长时间空转：

1. **15秒规则**: 如果连续 2-3 次尝试仍无法解决问题，立即停止并向技术主管报告
2. **报告格式**:
   ```markdown
   ## 🚫 卡住报告

   ### 现象
   - 正在做什么: <当前任务>
   - 卡在什么地方: <具体描述>

   ### 已尝试的方法
   - <方法1>: <结果>
   - <方法2>: <结果>

   ### 需要技术主管提供
   - <具体需要什么帮助>
   ```
3. 在得到技术主管的回复前，不要继续尝试

#### Bug 记录

开发过程中每发现并修复一个 bug，必须按以下格式记录到 `docs/smart-dev/bug-log.md`：

```markdown
## Bug #<编号>

### 基本信息
- **发现时间**: <ISO 时间戳>
- **发现位置**: <模块/文件路径>
- **发现人**: <工程师角色>
- **修复人**: <工程师角色>

### 现象描述
<bug 的具体表现，如错误信息、异常行为等>

### 根因分析
<导致 bug 的根本原因>

### 修复方式
<如何修复的，修改了哪些文件>

### 是否架构问题
- 是 / 否
- 如「是」，已同步通知技术主管
```

#### 架构问题升级规则

- 修复时发现是代码层面的问题 → 直接修复，记录即可
- 修复时发现是**架构设计问题** → 立即上报技术主管，由技术主管判定解决方案，工程师配合实施

### 步骤 5: 提交代码

```bash
git add <修改的文件>
git commit -m "feat: <功能描述>"
```

Commit 规范：
- `feat:` 新功能
- `fix:` 修复问题
- `refactor:` 重构
- `test:` 测试
- 各角色另有领域特定的 commit 类型

### 步骤 6: 合并到 dev

```bash
# 1. 先切换到 dev
git checkout dev

# 2. 拉取最新代码
git pull origin dev

# 3. 切回自己的 feature 分支
git checkout feature/<任务名>

# 4. 将 dev 的最新代码合并到 feature 分支
git merge dev

# 5. 如果有冲突，手动解决冲突后：
git add <冲突文件>
git commit -m "merge: 解决与dev分支的冲突"

# 6. 切回 dev
git checkout dev

# 7. 将 feature 分支合并到 dev
git merge feature/<任务名>

# 8. 推送到远程
git push origin dev
```

### 步骤 7: 汇报完成

向技术主管汇报：
```markdown
## 任务完成报告

### 任务
- **名称**: <任务名>
- **类型**: <frontend / backend / hardware>
- **分支**: feature/<任务名>

### 变更清单
- <文件1>: <变更说明>
- <文件2>: <变更说明>

### 测试情况
- <测试项1>: 通过/未通过
- <测试项2>: 通过/未通过

### 注意事项
- <需要其他工程师或技术主管知晓的事项>
```

## 质量要求

### 代码质量（通用）

- 命名使用驼峰式
- 不允许出现魔法数字
- 不允许出现中文定义(类,函数,变量)，全部使用英文
- 不允许出现字符串拼接，避免出现不必要的字符串常量
- 函数行数限制按角色约定执行，大函数应拆分为小函数

## 禁止事项（通用）

- 不要修改与自己任务无关的代码
- 不要跳过代码审查直接合并
- 不要 force push 到共享分支
- 不要将敏感信息提交到代码仓库
- 不要引入不需要的依赖包
